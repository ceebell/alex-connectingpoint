# ตรวจข้อความล่าสุดมาไม่ครบ

## ผลตรวจ 17/11/2026

ตรวจ Ubuntu ผ่าน API ภายในแบบอ่านอย่างเดียว พบ health ปกติและไม่มี webhook ในสถานะ PENDING, PROCESSING, FAILED หรือ NEEDS_ADMIN ณ เวลาตรวจ ตรวจการตั้งค่าจาก LINE API พบ `active=true` และ endpoint เป็น `https://hermes.salepie.online/api/line/webhook` ตรงกับแอป ([LINE webhook settings API](https://developers.line.biz/en/reference/messaging-api/#get-webhook-endpoint-information)) ส่วนตัวเชื่อม OA รายงาน `NEEDS_LOGIN` แม้ตั้ง `OA_CONNECTOR_ENABLED=true` แล้ว จึงยังยืนยันไม่ได้ว่าข้อความแอดมินจาก OA Manager ซิงก์ครบ ต้องเข้า OA ใหม่ด้วยบัญชีที่มีสิทธิ์ร้าน

อีกจุดหนึ่งพบจากโค้ดและทำซ้ำได้ด้วยข้อมูลทดสอบ: API เดิมคืน 200 ข้อความเก่าสุด และหน้าเว็บ poll ตามจำนวนหน้าที่เคยเปิด แชทที่ยาวจึงอาจไม่แสดงข้อความใหม่ที่อยู่อีกหน้า โดยไม่ขึ้นข้อผิดพลาด ยังไม่มีชื่อลูกค้า/เวลาของข้อความที่หายจริงเพื่อระบุว่ากรณีเฉพาะของผู้ใช้เกิดจากจุดใด

## พฤติกรรมหลังแก้

- เปิดแชทด้วย 200 ข้อความล่าสุด เรียงเก่าไปใหม่และเลื่อนไปข้อความล่าสุด ประวัติเก่าโหลดจากปุ่มด้านบน โดยคงตำแหน่งที่กำลังอ่าน
- การ poll เริ่มจากหน้าล่าสุดและอ่านย้อนจนถึงขอบเขตประวัติที่เปิดไว้ จึงรับข้อความใหม่ที่เกินหนึ่งหน้าได้ รวมข้อความ OA ที่นำเข้าช้าภายในช่วงที่เปิดอ่านไว้
- เปรียบเทียบ cursor ด้วยเวลา, event ID และ document ID เพื่อไม่ข้ามข้อความที่เวลา/event ID ตรงกันจากคนละแหล่ง
- คงประวัติและข้อความตอบที่ยังไม่ส่ง ปรับข้อมูลที่ถูกยกเลิกแล้วตามเซิร์ฟเวอร์ และไม่ให้ผลตอบกลับของลูกค้าคนเก่าทับคนที่เพิ่งเลือก
- เมื่อโหลดล่าสุดล้มเหลว คงข้อความเดิม แสดงสถานะให้ทราบ และลองใหม่ตามรอบ การตรวจ OA ล้มเหลว/หมดเวลาต้องไม่หยุดอ่านข้อความลูกค้าจาก backend
- แจ้ง `NEEDS_LOGIN` เป็นข้อความสั้นในแชท ไม่มีแบนเนอร์สีส้มเพิ่มเติม

## API และโค้ด

`GET /api/inquiries/{id}/context?latest=true` คืน `previous` สำหรับโหลดเก่าขึ้นด้วย `&before=<id>` ส่วน API เดิมที่ใช้ `after` ยังทำงานแบบเดิม ห้ามใช้ `after` กับ `latest=true` หรือใช้ `before` โดยไม่เปิด latest Cursor ต้องอยู่ในร้าน/ช่อง/บทสนทนาเดียวกัน และใช้ cursor ที่ถูกยกเลิกข้อความแล้วเพื่อโหลดหน้าต่อได้

ไฟล์หลัก: `backend/src/db/oa_sync.rs`, `backend/src/routes/admin.rs`, `backend/src/db/indexes.rs`, `frontend/src/lib/chat-history.ts`, `frontend/src/components/admin-workspace.tsx`

## สิ่งที่ต้องทำบนเครื่องจริง

ส่ง source และ Linux releases ที่ build บน Windows แล้วขึ้น Git จากนั้นบน Ubuntu:

```sh
cd ~/alex-connectingpoint
bash ./deploy-all.sh main
```

บน Windows รัน `login-oa.bat` แล้วลงชื่อเข้า LINE OA ด้วยบัญชีที่เข้าถึงร้าน ตรวจให้สถานะออกจาก NEEDS_LOGIN เป็น READY หรือ SYNCING แล้วโหลดข้อมูลล่าสุดใน Alex การ deploy แอปอย่างเดียวไม่ทำให้ session LINE OA ที่ต้องล็อกอินกลับมาเอง

ถ้ายังขาดข้อความ ให้ระบุชื่อลูกค้า เวลา และตัวอย่างข้อความเพื่อเทียบว่ามี event ใน backend หรือไม่ อย่าส่งข้อความซ้ำหรือสร้างข้อมูลลูกค้าใหม่เพื่อชดเชย เพราะยังต้องแยกการส่งเข้าระบบออกจากการแสดงผล

## การทดสอบ

Backend ใช้ MongoDB disposable และข้อความจำลอง 650 รายการจากสามแหล่ง ครอบคลุม timestamp/event ID ตรงกัน การแบ่งหน้าทั้งสองทิศ ข้อความมาช้า/ใหม่ cursor ถูกยกเลิกและการแยกร้าน/แชท Frontend มี unit tests สำหรับขอบเขตหน้าที่เปิด ข้อความใหม่เกินหลายหน้า การไม่ดึงประวัติเก่าที่ไม่เคยเปิด และการคงข้อความจากการส่งพร้อมกับ poll

Browser fixture ใน `data/chat-sync-check/` ทดสอบ Chrome/WebKit บน desktop/มือถือ รวมข้อความใหม่ 700 รายการ การยกเลิกข้อความ การ prepend โดยไม่กระโดด การโหลดล้มเหลวและการเปลี่ยนลูกค้าขณะคำขอเดิมยังไม่จบ ใช้ API จำลอง ไม่มีการส่งข้อความจริงเข้า LINE
