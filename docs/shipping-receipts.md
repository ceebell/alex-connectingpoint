# ใบเสร็จขนส่งและ Tracking

เมนู **พัสดุและ Tracking** อยู่ในหน้าหลัก แถบเมนูด้านซ้าย และบาร์มือถือ ใช้กับภาพใบเสร็จไปรษณีย์ไทยที่มีผู้รับหลายราย เช่น `prompts/image-11.png` บัญชีพนักงานที่ใช้งานหลังบ้านได้สามารถอัปโหลด ตรวจ และส่งข้อความได้ โดยเลือกได้เฉพาะออเดอร์ในร้าน/ช่อง LINE และสาขาที่ตนมีสิทธิ์

## วิธีใช้

1. อัปโหลดภาพใบเสร็จ ระบบเก็บภาพก่อนแล้วเข้าคิวอ่าน กลับมาติดตามได้แม้ปิดหน้าเว็บ ภาพ JPEG/PNG ที่ backend รับต้องไม่เกิน 8 MB; browser ช่วยแปลงรูปและรักษาความละเอียดของใบเสร็จแนวยาว
2. ระบบแยกชื่อผู้รับ เลข Tracking รหัสไปรษณีย์ บริการ และค่าขนส่งต่อราย พร้อมข้อความอ้างอิงจากภาพ ค่าขนส่งรายพัสดุรวมค่าบริการเพิ่มเติมของรายนั้น หากผลรวมต่างจากยอดท้ายใบเสร็จจะขึ้นให้ตรวจ ภาพอ่านไม่ออกให้เว้นว่าง ไม่เดาตัวเลขหรือเปลี่ยน O เป็น 0
3. ระบบจับคู่ชื่อที่อ่านได้กับชื่อในบิล ชื่อในโปรไฟล์ลูกค้าที่แอดมินบันทึก ชื่อ LINE/LINE OA และชื่อที่แอดมินตั้งในแชท แสดงชื่อ/รูปแชทที่แนะนำเมื่อมีลูกค้าตรงอย่างชัดเจนเพียงคนเดียว (ลูกค้าคนเดียวมีหลายออเดอร์ได้) ถ้าชื่อซ้ำหลายคน ผลยังมีหน้าต่อไป หรือชื่อคล้ายกันไม่ชัดเจน จะไม่แนะนำคนใดคนหนึ่ง ตรวจการ์ดและเลือกออเดอร์ด้วยตนเองทุกครั้ง ไม่มีการเลือกหรือผูกออเดอร์อัตโนมัติ ค้นด้วยชื่อผู้รับ ชื่อโปรไฟล์ ชื่อในแชท ชื่อในบิล หรือเลขออเดอร์ได้ หลังบันทึกและเปิดใหม่ชื่อบนการ์ดใช้ชื่อแชทล่าสุด โดยยังแสดงชื่อบนใบเสร็จแยกกัน
4. ตรวจชื่อ/ออเดอร์ในกรอบผู้รับ Tracking และข้อความที่จะส่ง แล้วกด **ส่งข้อความให้ลูกค้าคนนี้** ใต้ช่องข้อความ ระบบบันทึกข้อมูลปัจจุบันกับออเดอร์ก่อน แล้วจึงส่งให้ลูกค้าคนที่เลือก ถ้าต้องการเตรียมไว้ก่อนให้กด **บันทึก Tracking กับออเดอร์นี้** ซึ่งยังไม่ส่งข้อความ ไม่มีการแก้ยอด/ค่าขนส่งในบิล Alex
5. ข้อความเข้าบทสนทนา LINE เดิมและประวัติแชทในแอป แสดงผลส่งสำเร็จหรือยังไม่ยืนยัน พร้อมวันเวลา/แอดมินที่ส่ง หากบันทึกไม่สำเร็จจะไม่เรียกส่ง หากเริ่มส่งแล้วแต่ผลตอบกลับขาดช่วง ให้ตรวจผลล่าสุดก่อนลองคำขอเดิม

เลข Tracking ไปรษณีย์ไทยรับรูปแบบอักษร 2 ตัว + ตัวเลข 9 ตัว + TH รวม 13 ตัว ตรวจรูปแบบและตัดช่องว่าง/ขีด ไม่ได้ตรวจสถานะหรือความเป็นเจ้าของเลขกับ API ไปรษณีย์ แอดมินต้องเทียบภาพต้นฉบับก่อนส่ง หากแก้ข้อความเองต้องคงเลข Tracking ของรายการนั้นอยู่ในข้อความ

## ข้อความมาตรฐาน EMS

ช่องข้อความของพัสดุใหม่เตรียมข้อความตามนี้ และแทนเลข Tracking ของพัสดุรายการนั้นโดยตัดช่องว่าง/ขีดและใช้ตัวพิมพ์ใหญ่:

```text
ส่งของเรียบร้อยค่ะ ✨ (ems)
เลขที่ Tracking: {{เลข tracking จาก ems}}

สามารถเช็คสถานะได้ที่ https://track.thailandpost.co.th
```

ปุ่ม **ส่งข้อความให้ลูกค้าคนนี้** อยู่ใต้ข้อความของแต่ละรายการ ต้องเลือกออเดอร์ที่พร้อมและตรวจเลขพัสดุก่อน ปุ่มนี้บันทึกแล้วส่งได้ในคลิกเดียวโดยไม่ต้องกดบันทึกแยกก่อน การเปิดหน้า ค้นลูกค้า หรือบันทึกไว้ก่อนจะไม่ส่ง LINE

แอดมินแก้ข้อความได้ ข้อความที่บันทึกไว้แล้วจะเปิดตามข้อความเดิม รวมถึงข้อความที่เคยแก้เอง หากต้องการเปลี่ยนกลับเป็นรูปแบบข้างต้นให้กด **ใช้ข้อความมาตรฐาน** ระบบเติมเลข Tracking ปัจจุบันแล้วรอให้กดส่ง เมื่อเริ่มส่งแล้วช่องข้อความและการแก้ผู้รับจะถูกล็อก การลองส่งคำขอเดิมยังใช้ version/LINE retry key เดิมและไม่บันทึกข้อความใหม่ทับ

## ชื่อจากบิลหรือโปรไฟล์กับชื่อที่แสดงในแชท

ชื่อจริงบนใบเสร็จอาจต่างจากชื่อเล่นใน LINE ระบบใช้ชื่อจริงเพื่อค้น แต่แสดงชื่อ/รูปของ LINE user เดียวกับหน้าแชท โดยไม่เปลี่ยนชื่อแชทให้เป็นชื่อในบิล การเชื่อมใช้ LINE user ID และ inquiry ID ที่ตรวจตรงกัน ไม่เดาจากชื่อหรือรูปอย่างเดียว

| แหล่งค้นชื่อ | ฟิลด์ |
|---|---|
| ชื่อในบิลที่ส่งจาก Connecting Point | `alex_submissions.customer.name` |
| ประวัติบิลรุ่นก่อนที่ยังไม่มี customer snapshot | `review_input.customer_name`, `input.customer_name`, `payload.orderDetail.customerName` ใน `alex_submissions` |
| ชื่อในโปรไฟล์ลูกค้าที่แอดมินแก้ | `customer_profiles.display_name` |
| ชื่อที่ตั้งเฉพาะในแชท | `customer_aliases.custom_name` |
| ชื่อ LINE / OA | `line_users.display_name`, `line_users.oa_display_name` (OA ใช้เมื่อเปิด connector) |
| โน้ตที่แอดมินบันทึกในแชท | `customer_notes.text` ของลูกค้าคนนั้น |
| โน้ตในข้อมูลโปรไฟล์ลูกค้า | `customer_profiles.notes` |

ชื่อบนการ์ดใช้ชื่อที่แอดมินตั้งในแชทก่อน ตามด้วยชื่อ OA เมื่อเปิดใช้งาน แล้วจึงชื่อ LINE รูปใช้ `line_users.picture_url` เหมือนหน้าแชท ชื่อจากโปรไฟล์หรือบิลแสดงแยกใต้ชื่อแชทพร้อมระบุแหล่งที่พบ

ลำดับหลักฐานสำหรับลูกค้าแต่ละคนคือ **ชื่อในบิล → ชื่อในโปรไฟล์/ชื่อแชท → โน้ต** หากหาแหล่งก่อนหน้าที่ตรงกับชื่อผู้รับไม่พบจึงใช้แหล่งถัดไป แม้โปรไฟล์จะสะกดตรงกว่าชื่อบิลบางส่วน เมื่อบิลตรงอยู่แล้วจะยังแสดงบิลเป็นแหล่งหลัก ชื่อซ้ำคนอื่นยังแสดงแยกให้ตรวจ ไม่ใช้ลำดับนี้รวมคนที่ชื่อเหมือนกันเป็นคนเดียว

การค้นในโน้ตใช้ข้อความปัจจุบันที่แอดมินบันทึก ไม่ค้นประวัติ `history` หรือชื่อไฟล์/รูปแนบ และไม่ส่งโน้ตไปให้ AI เดาชื่อ ต้องมีชื่อที่ค้นปรากฏจริง (อย่างน้อย 3 ตัวอักษรหลังปรับคำนำหน้า/ช่องว่าง) ไม่ใช้การสะกดใกล้เคียงในข้อความอิสระ `matched_name` ของผลจากโน้ตเป็นข้อความอ้างอิงรอบชื่อ ไม่เกิน 242 ตัวอักษรรวมเครื่องหมายตัดข้อความ พร้อม `match_source=customer_note` หรือ `profile_note` ผลจากโน้ตใช้คะแนน 80 เพื่อให้ตรวจด้วยตนเอง ไม่แนะนำออเดอร์จากโน้ตอัตโนมัติ

แม้มีออเดอร์ที่พร้อมผูกแล้ว หากจับคู่จากโน้ตจะแสดงกรอบหลักฐานโน้ตไว้ด้วย ให้เปิดแชทตรวจข้อความและเลือกออเดอร์เอง การค้นนี้ไม่แก้ชื่อในบิล โปรไฟล์ โน้ต หรือชื่อหัวแชท และยังตรวจร้าน/ช่อง LINE กับ LINE user/inquiry เดิมทุกครั้ง

แยกผลค้นลูกค้าออกจากออเดอร์ที่พร้อมผูก Tracking: `GET /api/admin/shipping/orders?query=...` คืน `orders`/`more` ตามเดิม และเพิ่ม `customer_matches`/`customers_more` แต่ละ chat match มี `line_user_id`, `inquiry_id`, `chat_customer`, `matched_name`, `match_source`, `match_score`, `submission_status` ไม่ส่งโทรศัพท์/ที่อยู่ของประวัติบิลในส่วนนี้

- ค้นประวัติ `alex_submissions` ได้แม้สถานะยังเป็น `SUBMIT_UNKNOWN` หรือไม่มี Alex Order ID จึงยังแสดงแชทที่ตรงกับชื่อจริง พร้อมปุ่มเปิดแชทได้
- การแสดงว่าเคยส่งร่าง (`SENT`) ยังไม่ยืนยันว่า Alex สร้างออเดอร์สำเร็จ ถ้าบิลเป็น `SUBMIT_UNKNOWN` จะแสดงให้ตรวจเลขออเดอร์ในแชท ไม่สร้างเลขหรือเปลี่ยนสถานะอัตโนมัติ
- แชทที่พบแต่ยังไม่มีออเดอร์ `CONFIRMED` พร้อม Alex Order ID เป็นการ์ดข้อมูลเท่านั้น ไม่มีตัวเลือกผูกบิล ปุ่มบันทึกยังใช้ไม่ได้จนกว่าแอดมินจะเลือกออเดอร์ที่พร้อมจากรายการจริง
- ชื่อซ้ำหลายคน รวมถึงมีหนึ่งคนที่ออเดอร์พร้อมแต่อีกคนยังไม่ยืนยัน จะไม่แนะนำคนแรกเป็นคนเดียว หากผลชื่อหรือออเดอร์ยังมีต่อให้ระบุชื่อเต็มเพิ่ม
- ตรวจร้าน/ช่อง LINE ทุกแหล่ง ตรวจสาขาก่อนใช้ข้อมูลประวัติบิล และตรวจ user/inquiry/บทสนทนา 1:1 ให้ตรงกันก่อนแสดงแชท ชื่อในโปรไฟล์เป็นข้อมูลแชทระดับร้านตามสิทธิ์แชทเดิม ไม่ใช้เป็นทางอ่านข้อมูลบิลข้ามสาขา

## ลบทั้ง batch

เลือกใบเสร็จที่อัปโหลดแล้ว กด **ลบทั้ง batch** ข้างปุ่มดูภาพต้นฉบับ และยืนยันชื่อ batch ระบบนำใบเสร็จพร้อมพัสดุทุกรายการออกจากหน้าพัสดุ ใช้ได้ทั้งระหว่างรออ่าน กำลังอ่าน อ่านล้มเหลว และอ่านสำเร็จ ถ้ามี batch อื่นจะเปิด batch ถัดไป ถ้าไม่มีจะแสดงหน้าอัปโหลดใหม่

- เป็นการลบออกจากการใช้งานด้วยสถานะ `DELETED` เก็บผู้ลบ เวลา รูปต้นฉบับ และประวัติ Tracking ภายในเพื่อการตรวจสอบ/ป้องกันส่งซ้ำ ไม่ลบออเดอร์ Alex หรือข้อความในแชทที่ส่งไปแล้ว
- batch ที่ลบแล้วไม่แสดงในรายการ เปิดรายละเอียด/รูปไม่ได้ บันทึกหรือส่ง Tracking ผ่าน URL เดิมไม่ได้ และ worker อ่านภาพไม่ทำให้กลับมาแสดง การอัปโหลดรูปเดิมหรือ retry คำขออัปโหลดเดิมไม่คืน batch ที่ลบแล้ว เลข Tracking ที่เคยบันทึกยังคงถูกสงวนเพื่อป้องกันซ้ำ
- ตรวจร้าน/ช่อง LINE และสิทธิ์ทุกสาขาของออเดอร์ที่ผูกอยู่ก่อนลบทั้ง batch หากไม่มีสิทธิ์ครบจะลบไม่ได้ ใช้ session/CSRF เดิม
- API `POST /api/admin/shipping/receipts/{receipt}/delete` ส่งซ้ำได้โดยไม่สร้างผลเพิ่ม คืน `{"deleted":true,"receipt_id":"..."}` ใช้ MongoDB lease ร่วมกับการบันทึก/ส่งเพื่อกันลบระหว่างดำเนินการ หากกำลังมีคำขออื่นให้รอแล้วลองใหม่ lease หมดอายุได้หาก process หยุด

## การเชื่อมข้อมูลและการส่งซ้ำ

- ใช้เฉพาะ `alex_submissions.status=CONFIRMED` ที่มี `alex_order_id` และ LINE user ที่ตรวจได้ ไม่ใช่การเดาจากชื่อแชทล่าสุด เก็บ `submission_id`, `inquiry_id`, `line_user_id`, `draft_id`, `draft_version`, `alex_order_id`, `alex_order_number` และ snapshot ลูกค้ากับ Tracking โดยตรง
- การค้นหาชื่อแยกคำนำหน้า เช่น K./คุณ และจัดอันดับชื่อใกล้เคียงจากชื่อในบิล/โปรไฟล์ลูกค้า/LINE/OA/ชื่อที่ตั้งในแชท จำกัดผล 15 ออเดอร์และ 15 ลูกค้าต่อการค้นหา ชื่อที่ใกล้เคียงไม่ใช่การอนุมัติ การค้นหาชื่อคลาดเคลื่อนใช้รายการล่าสุดไม่เกิน 1,000 ออเดอร์ การค้นชื่อที่ตรงจะหา LINE user/alias/โปรไฟล์ก่อนค้นออเดอร์เพิ่ม จึงเจอออเดอร์เก่านอก 1,000 รายการล่าสุดด้วย (ค้นชื่อสูงสุดแหล่งละ 1,000 ออเดอร์ตรงเพิ่ม 100 รายการ ประวัติบิลสำหรับจับคู่แชท 100 รายการ และ inquiry จากชื่อ 100 รายการ) ถ้าแหล่งข้อมูลเต็มเพดานจะแจ้งว่ายังมีผลเพิ่มเติม หากมีผลมากหรือเป็นชื่อคลาดเคลื่อนในรายการเก่าให้ระบุชื่อ/เลขออเดอร์เต็ม
- ไม่ใช้ Tracking เดียวซ้ำในสองแถวของร้าน/ช่อง LINE เดียวกัน อัปโหลดรูปเดิมซ้ำคืนใบเสร็จเดิมแทนการอ่านหรือสร้างข้อมูลซ้ำ การแก้แถวก่อนส่งใช้ version เพื่อกันการเขียนทับกัน
- เมื่อเริ่มส่งจะล็อกผู้รับ เลข Tracking และข้อความ การลองส่งใหม่ใช้ LINE retry key เดิม ไม่สร้างคำขอใหม่ ถ้า LINE รับแล้วแต่ตอบกลับขาดช่วง การตรวจผลจะอ่านประวัติ outbound ที่เก็บไว้และอัปเดตเป็นส่งแล้ว
- คำขอที่ยังไม่ยืนยันเกิน 23 ชั่วโมงจะไม่ส่งซ้ำผ่านปุ่มนี้ เพื่ออยู่ภายในช่วง 24 ชั่วโมงที่ LINE เก็บ retry key ตาม [คู่มือ LINE](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/) ต้องตรวจแชท LINE ด้วยตนเอง การรับคำขอของ LINE ไม่ใช่หลักฐานว่าลูกค้าอ่านหรือได้รับข้อความเสมอไป ไม่มีการส่งข้อความอัตโนมัติขณะอ่านภาพ จับคู่ หรือเปิดประวัติ

## Backend และการเก็บข้อมูล

- `backend/src/models/shipping.rs`: schema และการตรวจภาพ/ผล OCR/ชื่อ/Tracking/ยอดเป็นสตางค์
- `backend/src/db/shipping.rs`: คิว OCR จับคู่ออเดอร์ บันทึก ตรวจสิทธิ์ และส่งผ่าน `db/outbound.rs` เดิม
- `backend/src/routes/shipping.rs`: endpoints ภายใต้ `/api/admin/shipping` ผ่าน session/Bearer และ CSRF ของระบบเดิม
- `shipping_receipts`: ภาพอ้างอิง ผลอ่าน สถานะ `QUEUED`, `READING`, `READY`, `FAILED`, `DELETED` ผู้ทำรายการ และ lease ของการบันทึก/ส่ง/ลบ
- `shipping_trackings`: การผูกพัสดุกับออเดอร์ ข้อความ ประวัติผู้แก้ version และสถานะ `READY`, `SENDING`, `SEND_FAILED`, `SENT`
- ภาพอยู่ใน GridFS แยกร้าน/ช่อง LINE เป็นเอกสารอ้างอิงถาวร ไม่มี URL สาธารณะ ต้องล็อกอินจึงเปิดภาพได้ ไม่ใช้วันหมดอายุของรูปแชท LINE

OCR ใช้ `HERMES_API_URL`, `HERMES_API_KEY`, `HERMES_MODEL` เดิม ผ่าน `ask_hermes_json` ซึ่งตรวจว่า extraction profile ปิด tools ก่อนส่งภาพ ไม่ส่งรายชื่อลูกค้าหรือออเดอร์ไปให้โมเดลจับคู่เอง ข้อความในภาพเป็นข้อมูล ไม่ถูกประมวลผลเป็นโค้ดหรือคำสั่ง และไม่ได้รับสิทธิ์เขียนฐานข้อมูลหรือส่ง LINE ถ้า backend หยุดระหว่างอ่าน ภาพยังอยู่และกดอ่านอีกครั้งได้

## การตรวจสอบและ deploy

ทดสอบ OCR/LINE ด้วย mock และ MongoDB disposable รวมชื่อซ้ำ แยกร้าน/สาขา ค่าขนส่ง Tracking ซ้ำ กดส่งซ้ำ ผลตอบกลับขาดช่วง และ profile AI ที่เปิด tools โดยไม่ส่งข้อความจริงและยังไม่ได้วัดความแม่นยำ OCR จาก Hermes ของร้านจริง

รอบเพิ่มลบ batch/จับคู่ชื่อแชท: backend fmt/clippy ผ่าน และ tests รวม 85/85 (รวม MongoDB integration); frontend lint/TypeScript/tests 64/64 และ Linux production build ผ่าน Browser fixture `data/shipping-batch-check/` ผ่าน Chrome/WebKit 16 กรณีที่ 1440/375/320px ครอบคลุมชื่อซ้ำหลายคน ลูกค้าคนเดียวหลายออเดอร์ ไม่มีผลตรง การคงชื่อแชทหลังบันทึก/รีเฟรช ยกเลิกการลบ ลบล้มเหลวแล้วลองใหม่ ลบขณะรออ่าน/กำลังอ่าน/อ่านไม่สำเร็จ ผล poll เก่ากลับมาหลังลบ และลบ batch สุดท้าย ตรวจภาพ desktop/มือถือแล้ว ไม่มี page error หรือคำขอหลุด fixture ไม่ส่ง LINE หรือสร้างออเดอร์จริง

รอบเพิ่มชื่อโปรไฟล์และประวัติบิลที่ยังไม่ยืนยัน: backend fmt/clippy/tests รวม 86/86 และ frontend lint/TypeScript/tests 65/65 ผ่าน Linux production releases build บน local ทั้งสองส่วน Browser fixture `data/shipping-profile-check/` ผ่าน Chrome/WebKit 12 กรณี รวมชื่อจากบิล `SUBMIT_UNKNOWN` ชื่อจากโปรไฟล์ที่ต่างจากชื่อแชท/ชื่อในบิล การแสดงรูป/ลิงก์แชทและเปิดใหม่ ออเดอร์ที่พร้อมกับลูกค้าชื่อซ้ำที่ยังไม่ยืนยัน ผลค้นไม่ครบ และผลคำขอค้นเก่ากลับมาช้า ตรวจชุดลบ batch เดิมซ้ำผ่าน 16 กรณี รวม 28 กรณี ตรวจภาพ desktop/มือถือแล้ว ไม่มี page error หรือคำขอหลุด fixture ตรวจกรณีผู้ใช้ระบุผ่าน GET บน server พบชื่ออยู่ในร่าง SENT แต่ประวัติบิลเป็น SUBMIT_UNKNOWN และไม่มีเลขออเดอร์ ไม่แก้ข้อมูลบิลหรือส่งข้อความจริง

รอบเพิ่มโน้ตเป็นแหล่งสำรอง: backend fmt/clippy/tests รวม 88/88 และ frontend lint/TypeScript/tests 66/66 ผ่าน Linux production releases build บน local ทั้งสองส่วน ทดสอบลำดับบิลก่อนโปรไฟล์ก่อนโน้ต ชื่อไทย/อังกฤษในข้อความปัจจุบัน ความยาวข้อความอ้างอิง ไม่จับคำสะกดคล้าย ไม่ค้น history/ชื่อรูป แยกร้าน/ช่อง และไม่อ่านบิลข้ามสาขาผ่านโน้ต Browser fixture `data/shipping-notes-check/` ผ่าน Chrome/WebKit 8 กรณี รวมโน้ตแชท/โปรไฟล์ ไม่มีออเดอร์ ออเดอร์พร้อมแต่ยังต้องเลือกเอง และโน้ตชื่อซ้ำ ทดสอบชุดบิล/โปรไฟล์เดิมซ้ำผ่าน 12 กรณี รวม 20 กรณีที่ 1440/375/320px ตรวจภาพ desktop/มือถือแล้ว ไม่มี page error หรือคำขอหลุด fixture ไม่ส่งข้อความหรือแก้ข้อมูล production

รอบข้อความมาตรฐานและปุ่มส่งใต้ข้อความ: frontend lint/TypeScript/tests 66/66 และ Linux production build ผ่าน Browser fixture `data/shipping-message-check/` ผ่าน Chrome/WebKit 20 กรณีที่ 1440/375/320px รวมข้อความตรงรูปแบบ เลขพัสดุแยกแต่ละลูกค้า ส่งโดยบันทึกก่อนในคลิกเดียว บันทึกไว้ก่อนแล้วค่อยส่ง เก็บข้อความที่แก้เอง คืนข้อความมาตรฐาน บันทึกล้มเหลวหรือข้อความไม่มีเลขแล้วไม่ส่ง retry โดยไม่บันทึกทับ และติดตามผลเมื่อคำตอบส่งขาดช่วง ตรวจภาพ desktop/มือถือแล้ว ไม่มี page error หรือคำขอหลุด fixture ไม่มีการส่ง LINE จริง Backend ไม่เปลี่ยนในรอบนี้

Windows build บน local ด้วย `build-all.bat` หรือ build เฉพาะส่วนที่แก้ แล้วผู้ใช้รัน `rungit.bat "Add shipping receipt extraction and reviewed tracking delivery"`

Ubuntu ใช้ release ที่ compile แล้ว:

```bash
cd ~/alex-connectingpoint
bash ./deploy-all.sh main
```

ไม่ต้องเพิ่ม env, ติดตั้ง OCR package, หรือ build โปรแกรมบน Ubuntu เมื่อ Hermes สำหรับอ่านภาพพร้อมใช้งานแล้ว
